## Regla de oro

1. Consultar este archivo antes de proponer o aplicar un fix para no duplicar soluciones.
2. Todo bug nuevo se registra con ID incremental, fecha, módulo, síntoma, causa, fix y estado; no se elimina al cerrarse.
3. Ningún bug pasa a `Resuelto` sin evidencia de validación (comando, test o smoke test) anotada en la fila.
4. Si un bug reaparece, se reabre el mismo ID con referencia cruzada; no se crea un duplicado.
5. Si el fix queda parcial o pendiente, el estado es `Abierto` o `Advertencia`, nunca `Resuelto`.

## Lecciones

- Antes de crear un router, verificar el entrypoint real de despliegue. El único entrypoint es `app.main:app`; todo router nuevo debe registrarse ahí.
- `requirements.txt` es exclusivo del runtime de la API. Dashboards, scrapers y workflows usan sus propios archivos de dependencias.
- Al eliminar scripts, actualizar en el mismo cambio los workflows, Procfile y documentación que los referencian.
- Consultar BUGS.md antes de proponer un fix para no duplicar soluciones.
- Antes de pushear a Railway, validar con `docker build` y un contenedor healthy; stagear solo archivos de runtime y nunca `.env*`, cookies o secretos untracked.
- No instalar `slowapi` ni paquetes que eleven Starlette: por BUG-005 el rate limit se implementó en memoria con stdlib (`app/core/security.py`).
- Los endpoints públicos comparten `verify_api_key` + `enforce_rate_limit` vía `include_router(dependencies=...)`; `/health` y `/ready` se dejan sin API Key para los healthchecks de Railway.
- Las claves nuevas `sb_*` requieren una versión reciente de supabase-py (validado con 2.34.1). Además, un RPC puede no ser ejecutable con la publishable key: probar con service role y registrar el permiso.
